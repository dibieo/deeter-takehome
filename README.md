# Neural Machine Translator — English ↔ French

A full-stack machine translation application comparing two sequence modeling paradigms:

| Architecture | Approach | Parameters |
|---|---|---|
| **GRU (Recurrent)** | Bidirectional encoder → single hidden state → GRU decoder | ~42 M |
| **Transformer** | Multi-head self-attention + cross-attention + positional embeddings | ~18 M |

Both models are trained from scratch on the [Tatoeba English–French corpus](http://www.manythings.org/anki/) (~190 k sentence pairs) and support **bidirectional translation** (EN→FR and FR→EN).

## Quick start

### 1 — Install dependencies

```bash
pip install -r requirements.txt
```

### 2 — Prepare the models

**Option A — Migrate the pre-trained notebook weights (fastest for EN→FR)**

The repository includes the weights from the original research notebook
(`models/notebook_rnn_en_fr.keras` and `models/notebook_transformer_en_fr.keras`).
The migration script re-wires the input names and saves the vocabularies:

```bash
python -m backend.migrate          # builds EN→FR models + vocabs
python -m backend.train --dir fr_en  # then train FR→EN (required for reverse direction)
```

**Option B — Train everything from scratch**

```bash
python -m backend.train            # EN→FR + FR→EN, both architectures
```

Training time on a GPU: ~20 min total. On CPU this will take longer.

Artefacts written to `models/`:

| File | Description |
|---|---|
| `rnn_en_fr.keras` | GRU model, English → French |
| `rnn_fr_en.keras` | GRU model, French → English |
| `transformer_en_fr.keras` | Transformer, English → French |
| `transformer_fr_en.keras` | Transformer, French → English |
| `vocab_*.json` | Tokenizer vocabularies (20 k tokens each) |
| `config.json` | Shared hyper-parameters |

### 3 — Start the server

```bash
uvicorn backend.app:app --reload
```

Open **http://localhost:8000** in your browser.

## API

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/translate` | Translate text |
| `GET` | `/api/status` | Which models are loaded |
| `GET` | `/api/health` | Liveness probe |

### POST /api/translate

```json
// Request
{
  "text": "Where is the train station?",
  "source_lang": "en",
  "target_lang": "fr",
  "model": "transformer"
}

// Response
{
  "translation": "où est la gare",
  "model": "transformer",
  "direction": "en→fr"
}
```

`model` accepts `"rnn"` or `"transformer"`.  
`source_lang` / `target_lang` accept `"en"` or `"fr"`.

## Architecture notes

### GRU seq2seq

```
[English tokens] → Embedding → Bidirectional GRU → encoder state
                                                       ↓
[French tokens]  → Embedding → GRU(initial_state) → Dropout → Dense(vocab) → softmax
```

The entire source sentence is compressed into a single 1024-dimensional vector.  
Decoding is autoregressive: each predicted token is fed back as the next decoder input.

### Transformer

```
[English tokens] → PositionalEmbedding → TransformerEncoder (self-attention) → enc_out
                                                                                    ↓
[French tokens]  → PositionalEmbedding → TransformerDecoder (self + cross-attention)
                                                              ↓
                                                          Dropout → Dense(vocab) → softmax
```

The encoder output attends to all source positions simultaneously. The decoder additionally  
attends to the encoder output via cross-attention, making long-range dependencies tractable.

### Training details

| Setting | Value |
|---|---|
| Vocabulary size | 20 000 tokens per language |
| Max sequence length | 30 tokens |
| Batch size | 64 |
| Optimiser | Adam |
| Loss | Sparse categorical cross-entropy (padded positions masked) |
| GRU embed / hidden dim | 256 / 1024 |
| Transformer hidden / ffn dim | 256 / 2048, 8 heads |
| Early stopping patience | 5 epochs (GRU), 5 epochs (Transformer) |

## Design decisions

**Why greedy decoding?**  
Beam search would improve BLEU scores, but greedy decoding keeps latency low for an interactive demo and makes the two architectures directly comparable.

**Why share a single server for API + frontend?**  
FastAPI mounts the `frontend/` directory at `/`, so there's no CORS configuration needed and deployment is a single `uvicorn` command.

**Why four separate models instead of one bidirectional model?**  
Each direction has its own vocabulary distribution and token-frequency ordering. Separate models are simpler to reason about and easier to swap out independently.
